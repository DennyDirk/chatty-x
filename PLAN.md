## Purpose / Big Picture


Владелец подключает до трёх личных Telegram-аккаунтов через TDLib, выбирает до 100 личных чатов и включает естественные текстовые ответы. Приложение понимает текст, фотографии и голосовые, объединяет серии входящих и хранит память отдельно для каждого собеседника. Ручной ответ из браузера или другого Telegram-клиента ставит чат на паузу до явного возобновления.

Первый релиз: один владелец, десять одновременно активных диалогов, Linux VPS 4 vCPU / 8 GB RAM как начальная конфигурация для проверки. Русский адаптивный интерфейс, светлая/тёмная тема. Нет публичной регистрации, тарифов, групп, каналов, секретных чатов, звонков, исходящего аудио, обработки видео/документов, платежей и инициативных сообщений. Второй канал существует только как FakeMessagingAdapter для тестов.

## Surprises & Discoveries


2026-09-26, отправка: работающий Telegram-стенд имеет WORKERS_ENABLED=false. Этот флаг останавливает DeliveryService.tick вместе с генерацией: API сохранял ручные сообщения как READY, хотя их никто не обрабатывал. Агрегат очереди показал четыре WEB_OWNER/READY, подключение READY с enabled=false, глобальное enabled=false и паузу у всех чатов; ключ OpenAI не настроен. Успешный импорт не доказывает работоспособность отправки. Содержимое сообщений и секреты не читались. При браузерной проверке выяснено, что текст ручного ответа виден в блоке очереди до доставки; Playwright теперь ждёт отдельного подтверждённого WEB_OWNER в истории, а не только текста на странице.

2026-09-26, повторное подключение: при диагностике ошибки TELEGRAM_NOT_CONNECTED сводный запрос к тестовому стенду показал один аккаунт AUTHORIZING с enabled=false. Причина завершения прежней сессии этим не установлена. Интерфейс переписки не знал статуса аккаунта, не переводил код ошибки и не предлагал вход; ConnectionService.select сохранял selected до проверки готовности импорта. Добавлены статус подключения в DTO чата, проверка до изменения выбора и доступ к существующей форме входа прямо из переписки.

2026-09-25, импорт: старый обработчик сохранял признак занятости только в памяти процесса и выставлял IMPORTING уже после запуска потока. Повторная загрузка активного чата не ставила mode на паузу, отмена не перепроверялась после сетевого ответа, а память ставилась в очередь даже после отмены. Состояние импорта теперь хранится в БД; изменения страницы и прогресса фиксируются одной транзакцией после проверки запуска. Telegram отдаёт время в секундах, поэтому начало окна импорта также фиксируется с секундной точностью. Живое событие, пришедшее после своей страницы истории во время импорта, сохраняет происхождение; давний повтор не превращается в новый вопрос.

2026-09-24, авторизация: прежняя ветка beginAuthorization для phone у существующего клиента не меняла способ входа. Ошибки setTdlibParameters/requestQrCodeAuthentication оставались в незавершённых ожиданиях, а запоздалый getMe мог вернуть READY после отключения. Регрессионные тесты воспроизводят эти случаи без аккаунта. Первый React-прогон имел один сбой из-за проверки ссылки до доставки асинхронного обновления QueryClient; тест исправлен ожиданием наблюдаемого изменения, повторный прогон успешен.

2026-09-24: официальный Java JsonClient позволяет использовать JNI с JSON-контрактами без зависимости бизнес-кода от сгенерированного TdApi. Сборка из ревизии ea97bcdd3a15523c58ddfe772b4547187cf5bbeb в infra/Dockerfile.tdlib завершилась экспортом chatty-x-tdlib:ea97bcdd. JNI прошёл проверку исполнения через обычный classpath и production PropertiesLauncher; live-операции пока не проверены. Docker Desktop доступен; backend-проверки используют Linux-контейнер Java 25. PowerShell на этой машине завершался ошибкой CET, команды выполнялись через cmd.exe.

Первый набор интеграционных тестов подтвердил дедупликацию, объединение серии, отбрасывание старой генерации, ручную паузу, отсутствие повтора UNKNOWN, изоляцию памяти и конкурентный бюджет. Проверка обнаружила отмену ручного сообщения при глобальной остановке: исправлено ограничением инвалидации на source=AUTOMATION. Установка нового Vitest потребовала исправления npm lockfile; чистая npm ci проверяется отдельно от локальной сборки.

Первоначально системная Java была 21, Node 22.23.1, Maven отсутствовал, Docker engine был остановлен. На 2026-09-24 Docker Desktop работает, проверки запускаются через Compose. Не менять системную защиту ради оболочки.

Самопроверка DeliveryService обнаружила повторную запись last_activity и задания памяти при дублирующем подтверждении, возможность позднего FAILED заменить SENT и сброс WAITING при подтверждении предыдущей отправки. Исправления проверены WorkflowIT; буфер подтверждений сохраняет успешное событие, блокировки всегда берутся в порядке «чат, затем подтверждение». Пограничный бюджет сравнивается через >=; ручная отправка сохраняется.

Playwright на http://web-e2e выявил TypeError: crypto.randomUUID is not a function до обращения к API. После замены ключа на getRandomValues сценарий полностью прошёл. Скриншоты проверены: на 390 × 844 нет горизонтального переполнения, управление доступно; автопрокрутка к последнему сообщению ещё требует доработки внутри M3.

В присланном владельцем журнале запуска Spring Boot корень ошибки — PostgreSQL SQLSTATE 28P01. Прямой запуск по умолчанию обращался к localhost:5432; Docker-база основного Compose не публикует этот порт, а на хосте он уже занят. Профиль local явно читает .env, использует DB_PASSWORD и отдельный PostgreSQL на 127.0.0.1:55432. Создание профиля не требует сброса существующих паролей или удаления томов.

TDLib sending_id непостоянен: помогает текущему сопоставлению, не гарантирует идемпотентность после аварии. sendMessage означает принятие библиотекой, не подтверждённую отправку. Текст/время не являются доказательством доставки.

Условия Telegram широко ограничивают AI-обработку данных, исключения могут требовать согласия участников конкретного чата. Авторизация не доказывает допустимость использования. До рабочего запуска установить основание; испытания — на синтетических данных и согласованных тестовых аккаунтах. Источники: https://telegram.org/tos/content-licensing и https://core.telegram.org/api/terms .

## Idempotence and Recovery


Импорт: запуск синхронно ставит чат на паузу и запрещает resume до полного завершения. Повтор start во время активного запуска не сбрасывает прогресс. Отмена обнуляет import_run_id под блокировкой чата: поздняя страница или ошибка старого запуска не могут изменить новый. После перезапуска startup-проверка переводит незаконченный импорт в IMPORT_INTERRUPTED; повтор начинается с головы истории, сохраняя уже загруженные сообщения. После отмены/ошибки задание начальной памяти не создаётся. Миграции V1–V5 сохранены; V6 только добавляет два nullable-поля.

Повторное нажатие того же способа входа не создаёт второй клиент. Переключение способа и повтор после ошибки сначала закрывают старый клиент. Неизвестный результат отключения не возвращает READY; повторное открытие каталога ждёт Closed. Остановка тестового Compose сохраняет его тома и не равна отзыву Telegram-сессии. Отзыв проверяется отдельно в списке устройств Telegram. Запуск или восстановление не включает автоматизацию.

Flyway migrations неизменяемы после применения. Ручные запросы уникальны по ключу, входящие по аккаунту/чату/ID. Задания/outbox обновляются транзакционно с блокировкой чата; сетевые вызовы не держат долгую транзакцию. Утративший lease обработчик не записывает новый результат. Ошибка AI не создаёт отправку. Restore требует разблокировки. Не удалять пользовательские volumes/сессии ради тестов; отдельные тестовые БД/каталоги.
